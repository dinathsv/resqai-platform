# Automatic weather inputs for risk assessment

The mobile prediction page asks people to choose their district and check risk. Weather estimates are fetched by the ML service. People can optionally use GPS for the weather location after selecting the district used for the model's area profile. Without GPS, the service uses a clearly labelled representative point in the selected district.

The result is an experimental assessment based on the **latest complete weather day**, not a live observation or a forecast of tomorrow. The source, location, weather date, period and retrieval time accompany the result. Weather varies within a district and the provider returns a model grid cell, so the assessment does not establish conditions at a particular house. The app keeps manual rainfall entry inside an advanced demonstration option.

## Weather and model inputs

`POST /predict/automatic` accepts a district and optionally a latitude/longitude pair. The service fetches [Open-Meteo ECMWF weather data](https://open-meteo.com/en/docs/ecmwf-api), calculates the daily inputs and passes them to the existing model:

- Daily precipitation and rainfall, plus the preceding 24, 48 and 72 hours of rain.
- Mean soil moisture for the 0–7 cm and 7–28 cm layers.
- Daily maximum temperature in °C and wind speed in km/h.
- Soil index calculated using the same layer weighting as the training dataset.

The application uses windows ending at midnight in `Asia/Colombo`. The training CSV does not record its source or timezone, so this explicit local-day convention still needs independent validation against real events. Preceding-hour rainfall timestamps are aligned with their accumulation intervals. Missing, malformed or incomplete weather data produces an unavailable response; it is not replaced with zero rainfall or assumed soil moisture. A short bounded cache reduces repeat requests and expired data is not used for a fresh assessment.

The monthly rainfall fields from the previous mobile form were ignored by the inference path and have been removed from that form. The fabricated annual rainfall display has also been removed. The existing `/predict` endpoint remains available for manual demonstrations and existing clients.

Rainfall threshold indicators are generated by ResQAI and do not represent an issued NBRO warning. Model probabilities are not a field-validated probability of flooding. Training uses a modeled dataset; weather integration alone does not validate prediction accuracy. Compare results against independent real events and time-separated validation data before making accuracy claims.

## Deploy and run

No Supabase SQL, payment service or change to SMSlenz is required.

1. Redeploy the **ML service** from `ml-models/` so its updated requirements and new endpoint are installed. It needs outbound HTTPS access to `api.open-meteo.com`.
2. Redeploy the Python API for the separate mobile OTP destination correction.
3. Confirm `EXPO_PUBLIC_ML_API_URL` points to the hosted ML service before building the Expo APK. The existing preview and production profiles in `mobile/eas.json` already declare the hosted URL. This is a public service URL, not a secret.
4. Rebuild and install the APK. Existing installed APKs do not gain these changes just because a backend is redeployed.

For local Docker, rebuild the ML and mobile services:

```sh
docker compose up -d --build ml-models mobile-app-web
```

For a physical phone using Expo development, use the development server's LAN address for the ML service, rather than the phone's own `localhost`. The services must be reachable on the same network.

The default provider API requires no key for this non-commercial student prototype. Its [free service has usage limits and no uptime guarantee](https://open-meteo.com/en/pricing). Review the provider's current terms before commercial deployment. The result displays source attribution.

## Verification

Automated ML tests isolate provider calls and cover complete windows, weather validation, caching and unavailable responses. Mobile TypeScript and export checks verify that the updated interface builds. A successful test run does not establish real-world disaster forecasting skill.
